# 版本號規範

> 本規範規定**版本號怎麼訂、何時遞增、存放在哪、如何維持一致**。
> 通用規範，任何專案皆適用。

---

## 1. 目的與適用範圍

### 1.1 目的

讓版本號本身就是資訊：使用者看到號碼跳動的位數，就知道這次升級會不會弄壞現有的用法。

### 1.2 適用對象

本規範**規範流程，不規範任何一份文件**。專案**不需要**、也**不應該**建立 `VERSION.md`——版本號的權威值在建置設定檔（見 §2.3），歷史在 `CHANGELOG.md`。多開一份文件只會多一個會不同步的地方。

### 1.3 本規範不管什麼

- 不管變更紀錄怎麼寫 → `CHANGELOG_RULES.md`
- 不管打包、tag、Release 頁面 → `RELEASE_RULES.md`

### 1.4 強制語彙

| 用詞 | 意義 |
| :--- | :--- |
| **必須** | 不做就是不合規（MUST） |
| **建議** | 有更好的理由才可以不做（SHOULD） |
| **可** | 自行斟酌（MAY） |

## 2. 版本號的格式與存放位置

### 2.1 格式

版本號**必須**遵循語意化版本（Semantic Versioning）：

```text
MAJOR.MINOR.PATCH
```

- 在 git tag、產物檔名、Release 標題中**必須**帶 `v` 前綴（`v1.0.0`）。
- 在設定檔欄位與 `CHANGELOG.md` 版本標題中**必須不**帶 `v`（`1.0.0`）。

### 2.2 單一來源

每個專案**必須**指定**一個**檔案的版本號欄位為**單一來源（single source of truth）**，並在 `DEVELOPER.md` §7 明確宣告。

### 2.3 同步清單

版本號通常同時存在於多處。專案**必須**在 `DEVELOPER.md` §7 列出**所有**需要跟著改的位置，逐一標明「手動」或「自動」：

```markdown
單一來源：`package.json` 的 `version`

| 位置 | 欄位 | 方式 |
| :--- | :--- | :--- |
| `package.json` | `version` | 手動（單一來源） |
| `<建置設定檔>` | `version` | 手動 |
| 產物檔名 | — | 自動 |
```

- 標為「自動」的位置**禁止**手動修改。
- **不需要**撰寫自動改版本號的腳本。一致性由 `RELEASE_RULES.md` 的發佈檢查清單**逐項核對**保證。
- 專案**可**提供**唯讀**的檢查指令，把各處版本號印出來供比對；此為選用。

### 2.4 遞增時機

- 版本號**必須**在**發佈時**遞增，不在每次 commit 時遞增。
- 開發期間的變更累積在 `CHANGELOG.md` 的 `[Unreleased]` 區塊。

## 3. 結構：三個位數的意義

### 3.1 MAJOR（主版本號）— `X.0.0`

> 關鍵字：**不向下相容**

升級後，既有的用法可能**無法繼續運作**，使用者或下游需要調整。

觸發時機：

- 修改或刪除既有的 API、函式簽名、資料結構、設定檔格式
- 徹底重構底層架構，導致舊介面失效
- 移除已標記為 Deprecated 的功能
- 從開發階段（`0.x.x`）進入第一個正式穩定版（`1.0.0`）

**跨 MAJOR 且整個實作被替換時**，舊實作的保留方式依 `DEVELOPER.md` §8 的分支保留規則辦理（舊實作以分支保留、不刪除，主分支走新實作）。

### 3.2 MINOR（次版本號）— `1.Y.0`

> 關鍵字：**向下相容的新功能**

新增功能或擴充，但既有用法**完全不受影響**。

觸發時機：

- 新增 API、元件、參數（預設值不改變原有行為）
- 將某功能標記為 Deprecated（尚未移除）
- 顯著的效能或處理邏輯改進，且輸出結果一致

### 3.3 PATCH（修訂號）— `1.0.Z`

> 關鍵字：**向下相容的修復**

只修錯，不加東西、不改介面。

觸發時機：

- 修復當機、資源洩漏、邏輯錯誤
- 修正介面文字、樣式跑版
- 修補安全性問題

## 4. 判斷規則

### 4.1 依 CHANGELOG 類別判斷

`CHANGELOG.md` 的 `[Unreleased]` 區塊出現了哪些類別，就決定版本號跳哪一位。**取其中最高者**：

| `CHANGELOG.md` 出現的類別 | 版本號 |
| :--- | :--- |
| `Removed`，或標註 **[破壞性變更]** 的 `Changed` | **MAJOR** |
| `Added`、`Deprecated`、不破壞相容性的 `Changed` | **MINOR** |
| `Fixed`、`Security` | **PATCH** |

### 4.2 對照表

| 變更類型 | 範例 | 版本號變動 | 向下相容 |
| :--- | :--- | :---: | :---: |
| 修復錯誤 | 修正計算未處理負數 | 1.0.0 → 1.0.1 | 是 |
| 安全修補 | 修補權限檢查缺漏 | 1.0.1 → 1.0.2 | 是 |
| 新增功能 | 增加匯出報表 | 1.0.2 → 1.1.0 | 是 |
| 標記棄用 | 宣告舊介面將於 2.0 移除 | 1.1.0 → 1.2.0 | 是 |
| 破壞性變更 | 設定檔格式變更，舊檔無法讀取 | 1.2.0 → 2.0.0 | 否 |

### 4.3 特殊階段

**開發階段 `0.y.z`**
API 隨時可能改變，不受向下相容約束。此階段**必須**在 `README.md` 明確告知使用者。

**預發佈版本**
於 PATCH 後加連字號與標籤，**必須**帶遞增序號：

```text
1.0.0-alpha.1    內部測試
1.0.0-beta.2     公開測試
1.0.0-rc.1       發佈候選
```

預發佈版本在 GitHub Release **必須**勾選 Pre-release（見 `RELEASE_RULES.md`）。

### 4.4 不可回頭

- **禁止**重複使用已發佈過的版本號。
- **禁止**降版。發佈後才發現問題，一律往前發新的 PATCH。
- **禁止**刪除或搬移已發佈的 tag 指向（舊版本的**淘汰**處置見 `RELEASE_RULES.md`）。

---

## 5. 範例與註解慣例

- 佔位符**必須**用角括號加繁中描述：`<版本號>`、`<建置設定檔>`。
- 範例版本號一律由 `1.0.0` 起算；虛構專案一律用 `MYAPP`。
- 表格中的版本變動**必須**寫成 `舊 → 新` 的完整形式，**禁止**只寫「+1」。

---

## 6. 禁止事項

- **禁止**建立 `VERSION.md` 或其他獨立的版本號文件。
- **禁止**在多處各自維護版本號而不宣告單一來源。
- **禁止**在設定檔欄位寫入 `v` 前綴，或在 tag／產物檔名省略 `v`。
- **禁止**為了「看起來比較成熟」而跳號（例如直接從 1.0.0 跳到 2.0.0）。
- **禁止**在單次發佈中同時遞增兩個以上的位數。
- **禁止**用日期當版本號（`2026.08.06`）——那不帶相容性資訊。
- **禁止**發佈未在 `CHANGELOG.md` 留下對應區塊的版本。

---

## 7. 檢查清單

發佈前逐項確認：

- [ ] `[Unreleased]` 的內容已確定，類別齊全
- [ ] 依 §4.1 判定要跳的位數，且只跳一位
- [ ] 新版本號未曾使用過，且大於前一版
- [ ] 單一來源已更新
- [ ] `DEVELOPER.md` §7 同步清單上的每一處手動位置都已更新
- [ ] 標為「自動」的位置未被手動改動
- [ ] 設定檔欄位不帶 `v`；tag 與產物檔名帶 `v`
- [ ] `CHANGELOG.md` 已將 `[Unreleased]` 轉為此版本號並填入發佈日
- [ ] 預發佈版本已帶標籤與序號
- [ ] 若為 MAJOR 且替換了整個實作，舊實作分支已依 `DEVELOPER.md` §8 建立
