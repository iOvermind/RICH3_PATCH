# DEVELOPER.md 撰寫規範

> 本規範規定 `DEVELOPER.md` **該寫什麼、怎麼寫**，不規定專案的技術選型。
> 通用規範，任何專案皆適用。

---

## 1. 目的與適用範圍

### 1.1 目的

讓一個**沒碰過這個專案的開發者**，照著文件從零把環境架起來、跑得動、改得動、驗證得了、交得出去——過程中不需要問任何人。

「沒碰過這個專案的開發者」包含**半年後的你自己**。

### 1.2 讀者

讀者是**要修改這個專案的人**，不是使用它的人。可以假設對方會用 git、會用終端機，但**不可**假設對方知道這個專案的任何約定。

### 1.3 邊界

- **用它** → `README.md`
- **改它** → `DEVELOPER.md`

### 1.4 本規範不管什麼

- 不管程式碼風格細節（縮排、命名）——那由各專案的 linter 設定決定，本文件只需指出設定檔在哪。
- 不管發佈流程 → `RELEASE_RULES.md`
- 不管版本號語意 → `VERSION_RULES.md`

### 1.5 強制語彙

| 用詞 | 意義 |
| :--- | :--- |
| **必須** | 不做就是不合規（MUST） |
| **建議** | 有更好的理由才可以不做（SHOULD） |
| **可** | 自行斟酌（MAY） |

---

## 2. 檔案位置與命名

- 檔名**必須**為 `DEVELOPER.md`，**必須**放在儲存庫**根目錄**。
- 編碼**必須**為 **UTF-8 無 BOM**，換行**必須**為 **LF**，檔尾**必須**留一個換行。
- 語言**必須**為**繁體中文**；指令、檔名、型別名、API 名稱保留原文。
- 單節過長時**可**外拆到 `docs/`，但必要章節的標題與摘要**必須**留在 `DEVELOPER.md`。

## 3. 結構：必要章節 / 選用章節

### 3.1 必要章節（依此順序）

順序即新人的實際動線：裝環境 → 跑起來 → 看懂 → 改 → 驗證 → 交出去。

| # | 章節 | 必須回答的問題 |
| :-: | :--- | :--- |
| 1 | 技術棧與系統需求 | 用什麼寫的？需要哪些工具、哪個版本？ |
| 2 | 環境建置 | 從乾淨的機器到能跑，要做哪幾步？ |
| 3 | 日常開發 | 怎麼啟動？怎麼熱更新？怎麼除錯？ |
| 4 | 目錄結構 | 東西放哪？我要改的檔在哪？ |
| 5 | 架構與關鍵設計決策 | 為什麼這樣切？哪些決定不能隨便推翻？ |
| 6 | 測試 | 怎麼跑？哪些會被略過？為什麼？ |
| 7 | 建置與產物 | 怎麼建？產出什麼？**版本號要同步改哪幾處？** |
| 8 | 分支、commit 與 PR 慣例 | 從哪開分支？訊息怎麼寫？舊版怎麼保留？ |
| 9 | 安全與敏感資料 | 什麼絕對不能進版控？權限開到哪？ |
| 10 | 已知陷阱 | 前人踩過哪些坑？ |

沒有內容的必要章節**必須**保留標題並註明現況（例如「目前無」），**不得**刪除。

### 3.2 選用章節

- CI / 自動化
- 資源、資料檔的產生工具
- 效能量測方式
- 對外相依服務與帳號申請流程

## 4. 撰寫規則

### 4.1 各必要章節的最低要求

**§1 技術棧與系統需求**
**必須**列出語言／執行期／建置工具及其**版本或最低版本**，以及作業系統限制。**禁止**只寫「Node」不寫版本。

**§2 環境建置**
**必須**是可逐步照做的編號步驟，從取得原始碼開始。每一步**必須**有可觀察的完成狀態（看到什麼輸出、產生什麼檔案）。

**§3 日常開發**
**必須**包含啟動指令、修改後如何反映、如何看到錯誤訊息（log 位置、除錯開關）。

**§4 目錄結構**
**必須**用樹狀圖列到「有意義的那一層」為止，每個項目**必須**有一句話說明職責。**禁止**貼出完整檔案清單，也**禁止**列出 `node_modules`、`target`、`dist` 等產生物。

**§5 架構與關鍵設計決策**
**必須**說明主要模組的職責與依賴方向。**必須**記錄「刻意這樣做」的決定與**理由**——只寫結論不寫理由，等於沒寫。重大且難以反轉的決策**建議**另立 ADR（`docs/adr/`）並在此連結。

**§6 測試**
**必須**寫出跑測試的指令，以及測試分類（單元／整合／回歸）。若有測試會因缺少外部檔案而被略過，**必須**說明：略過的條件、檔案該放哪、如何辨識「略過」與「失敗」。

**§7 建置與產物**
**必須**寫出建置指令與**每一個產物的名稱與用途**。
**必須**包含「版本號同步清單」（見 §4.2）。

**§8 分支、commit 與 PR 慣例**
**必須**寫明主要分支名稱、從哪開分支、commit 訊息格式。
**必須**包含**舊實作的保留規則**（見 §4.3）。

**§9 安全與敏感資料**
見 §4.4。

**§10 已知陷阱**
見 §4.5。

### 4.2 版本號同步清單（§7 必備）

版本號通常同時存在於多個檔案，不同步就會出現「安裝檔寫 v1.0.1、關於視窗寫 v1.0.0」。

**必須**在 §7 明確宣告：

1. **單一來源**——哪一個檔案的版本號是準的。
2. **同步清單**——所有需要跟著改的位置，逐一列出檔案與欄位。
3. 能由建置流程**自動衍生**的位置**必須**標明「自動」，並**禁止**手動修改。

範例（虛構專案 `MYAPP`）：

```markdown
### 版本號

單一來源：`package.json` 的 `version`

| 位置 | 欄位 | 方式 |
| :--- | :--- | :--- |
| `package.json` | `version` | 手動（單一來源） |
| `src-tauri/tauri.conf.json` | `version` | 手動 |
| `src-tauri/Cargo.toml` | `package.version` | 手動 |
| 產物檔名 | — | 自動（由建置腳本讀取單一來源） |
```

**不需要**撰寫自動改版本號的腳本；一致性由 `RELEASE_RULES.md` 的發佈檢查清單逐項核對。專案**可**提供**唯讀**的檢查指令（把各處版本號印出來比對），但非必要。

### 4.3 舊實作的保留規則（§8 必備）

當一次改版使**舊實作無法與新實作共存於主分支**時（技術棧更替、整體重寫）：

- 舊實作**必須**以分支保留，**禁止**直接刪除。
- 分支名稱**建議**用 `legacy/<簡短描述>`，並在 §8 記錄「這個分支是什麼、為什麼留、留到什麼時候」。
- 該分支**不再接受新功能**；僅在有明確理由時接受修正。
- 主分支（`main`）走新實作。
- 若舊實作是驗證新實作正確性的基準（oracle），**必須**在 §8 寫明驗證方式與解除保留的條件。

`VERSION_RULES.md`（MAJOR 節）與 `RELEASE_RULES.md`（舊版本處置節）交叉引用本條，實質規則以本條為準。

### 4.4 安全與敏感資料（§9 必備）

**必須**涵蓋且**只**涵蓋以下四項。編碼層次的安全（輸入驗證、注入防護等）不在本規範範圍。

| # | 項目 | 必須寫明 |
| :-: | :--- | :--- |
| 1 | 機密不進版控 | 哪些檔案／欄位是機密（金鑰、憑證、密碼、個人路徑、帳號），如何排除（`.gitignore` 條目），以及開發者本機該把它們放哪 |
| 2 | 權限最小化 | 程式向作業系統／執行期要求了哪些權限（檔案存取範圍、網路、系統 API），為什麼需要，以及刻意**不要**的權限 |
| 3 | 依賴來源與鎖檔 | 鎖檔（`package-lock.json`、`Cargo.lock` 等）是否進版控，安裝時用哪個指令（例如 `npm ci` 而非 `npm install`），第三方資源的來源 |
| 4 | 破壞性操作的保護 | 程式會覆寫或刪除使用者資料的地方，以及可回復機制（備份策略、是否覆蓋既有備份、如何還原） |

簽章、SmartScreen、產物校驗碼屬於**發佈**議題，寫在 `RELEASE_RULES.md`，不寫在此。

### 4.5 已知陷阱（§10 必備）

記錄開發過程中實際踩到、且**下一個人很可能再踩一次**的問題。

每一條**必須**用固定三段式：

```markdown
#### <一句話標題>

- **症狀**：你會看到什麼（錯誤訊息原文、異常行為）
- **原因**：為什麼會這樣
- **處置**：怎麼解決或怎麼避開
```

規則：

- 症狀**必須**寫實際可搜尋的字串（錯誤訊息原文），這是別人找到這一條的唯一途徑。
- **禁止**只寫「要注意 X」這種事後看不懂的句子。
- **踩到就補一條**——排除一個非顯而易見的問題後，在合併前補進本節。
- 陷阱若已被修掉且不會再發生，**必須**刪除該條，並在 `CHANGELOG.md` 記錄。
- 尚未踩到任何坑時，保留章節標題並寫「目前無」。

範例：

```markdown
#### 安裝完工具鏈後，已開著的終端機仍找不到指令

- **症狀**：執行建置指令時出現 `cargo: command not found`，但工具鏈確實已安裝完成
- **原因**：安裝程式只更新了系統的 PATH，不會影響已經開著的終端機工作階段
- **處置**：重開終端機；或讓建置腳本自行到預設安裝路徑尋找執行檔
```

### 4.6 一般撰寫規則

- 全文**只有一個** H1；必要章節用 H2。
- 程式碼區塊**必須**標註語言，指令**禁止**帶提示符。
- 庫內連結**必須**用相對路徑。
- 說明「為什麼」重於「是什麼」——指令本身看得懂，理由看不懂。

## 5. 範例與註解慣例

- 佔位符**必須**用角括號加繁中描述：`<專案名稱>`、`<版本號>`。
- 範例指令**必須**能原樣執行（佔位符除外）。
- 虛構專案一律用 `MYAPP`，虛構版本號一律 `v1.0.0`。
- **禁止**在範例中出現真實的金鑰、憑證檔名、本機絕對路徑或個人帳號。
- 註解一律繁中，說明理由而非複述指令。

---

## 6. 禁止事項

- **禁止**寫使用者導向的操作說明 → `README.md`。
- **禁止**寫逐版變更紀錄 → `CHANGELOG.md`。
- **禁止**寫發佈流程與產物命名 → `RELEASE_RULES.md`。
- **禁止**只寫結論不寫理由的設計說明。
- **禁止**貼出無法執行或未經驗證的指令。
- **禁止**留下 `TODO`、`待補`。
- **禁止**出現金鑰、憑證密碼、個人帳號、本機絕對路徑。
- **禁止**在 §10 以外的地方零散記錄陷阱。

## 7. 檢查清單

- [ ] 檔案在根目錄，UTF-8 無 BOM、LF、檔尾一個換行
- [ ] 十個必要章節齊全且順序正確
- [ ] §1 每項工具都標了版本或最低版本
- [ ] §2 在一台乾淨環境上實際照做過一次
- [ ] §4 目錄樹沒有列出產生物
- [ ] §5 每個設計決策都寫了理由
- [ ] §6 說明了測試被略過的條件與辨識方式
- [ ] §7 有版本號單一來源與完整同步清單
- [ ] §8 有舊實作保留規則，且分支命名與現況相符
- [ ] §9 四項全部覆蓋，且與 `.gitignore` 實際內容一致
- [ ] §10 每條都是三段式，症狀含可搜尋的錯誤原文
- [ ] 所有指令標了語言、無提示符、可原樣執行
- [ ] 沒有金鑰、絕對路徑、TODO
