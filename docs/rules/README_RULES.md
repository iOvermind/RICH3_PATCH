# README 與專案門面撰寫規範

> 本規範規定使用者第一眼看到的東西——`README.md` 與儲存庫的 **About**——
> **該寫什麼、怎麼寫**，不規定專案的技術選型。
> 通用規範，任何專案皆適用。

---

## 1. 目的與適用範圍

### 1.1 目的

讓任何人在**三十秒內**判斷「這個東西是不是我要的」，並在**五分鐘內**真的用起來。

### 1.2 讀者

README 的讀者是**使用者**——也就是**這個產物的消費者**：

| 專案型態 | 使用者是誰 |
| :--- | :--- |
| 桌面 / 行動應用程式 | 操作它的人 |
| 函式庫 (library) | 在自己專案裡引用它的開發者 |
| 命令列工具 (CLI) | 在終端機執行它的人 |
| 服務 / API | 呼叫它的人 |

### 1.3 邊界

用**「用它」還是「改它」**切，不用「技術/非技術」切：

- **用它** → `README.md`
- **改它** → `DEVELOPER.md`

因此環境建置、建置指令、測試、目錄結構、架構說明**一律不進 README**（見 §6）。

### 1.4 為什麼 About 也歸這份管

儲存庫的 **About**（簡介、網站、主題標籤）不是檔案，卻是**比 README 更早被看到**的東西——它出現在搜尋結果、Star 清單、分享連結的預覽裡。

它與 README 的「一句話定位」講的是同一件事，分開管的結果就是各寫各的：README 改了、About 留在半年前的版本，而**沒有人會發現**。所以兩者寫在同一份規範裡，並要求逐字一致（見 §4.7）。

### 1.5 本規範不管什麼

- 不管專案用什麼語言、框架、建置工具
- 不管 README 的視覺風格（emoji、徽章、排版偏好由專案自訂）
- 不管 `DEVELOPER.md`、`CHANGELOG.md` 的內容（各見其規範）
- 不管儲存庫的其他設定（分支保護、labels、可見性）

### 1.6 強制語彙

| 用詞 | 意義 |
| :--- | :--- |
| **必須** | 不做就是不合規（MUST） |
| **建議** | 有更好的理由才可以不做（SHOULD） |
| **可** | 自行斟酌（MAY） |

## 2. 檔案位置與命名

- 檔名**必須**為 `README.md`，**必須**放在儲存庫**根目錄**。
- 編碼**必須**為 **UTF-8 無 BOM**，換行**必須**為 **LF**，檔尾**必須**留一個換行。
- 語言**必須**為**繁體中文**；指令、檔名、API 名稱、專有名詞保留原文，首次出現時加中譯。

### 2.1 內容外拆

單一章節過長時，**可**把細節拆到 `docs/` 底下（例如 `docs/使用說明.md`），但：

- §3 的每個必要章節**必須**在 README 保留**標題與至少一段摘要**，再連結過去。
- **禁止**把 README 縮成只有連結的目錄頁。

### 2.2 About 存在哪裡

About 不是檔案，是儲存庫的設定。它沒有版本控制，**改了不會留下紀錄，也不會有人 review**——這正是它容易過時的原因，所以 §7 的檢查清單把它列為發佈前必查項。

---

## 3. 結構：必要章節 / 選用章節

### 3.1 必要章節（依此順序）

| # | 章節 | 必須回答的問題 |
| :-: | :--- | :--- |
| 1 | 專案名稱 + 一句話定位 | 這是什麼？給誰用？ |
| 2 | 這是什麼 / 能做什麼 | 它解決什麼問題？有哪些主要功能？ |
| 3 | 取得與安裝 | 去哪下載？需要什麼環境？怎麼裝？ |
| 4 | 快速開始 | 從裝好到看見結果，最短路徑是什麼？ |
| 5 | 常見問題 / 疑難排解 | 卡住了怎麼辦？ |
| 6 | 授權 | 我能拿它做什麼？ |
| 7 | 開發者入口 | 我想改它，去哪？（連結 `DEVELOPER.md`） |

順序**不得**調換。沒有內容的必要章節**必須**保留標題並註明現況（例如「目前無已知問題」），**不得**刪除。

### 3.2 選用章節

| 章節 | 建議放置位置 |
| :--- | :--- |
| 截圖 / 操作動畫 | 第 2 節之後 |
| 相容性對照表 | 第 3 節之內 |
| 已知限制 | 第 5 節之前 |
| 致謝與來源參考 | 第 6 節之前 |
| 變更紀錄連結（→ `CHANGELOG.md`） | 第 7 節旁 |

### 3.3 About 的欄位

| 欄位 | 必要性 | 內容 |
| :--- | :--- | :--- |
| 簡介（description） | **必填** | 與 README 的一句話定位**逐字相同**（見 §4.7） |
| 主題標籤（topics） | **必填** | 涵蓋三個面向，見 §4.8 |
| 網站（website） | 選填 | 只填「離開這個儲存庫也能用」的東西，見 §4.9 |

## 4. 撰寫規則

### 4.1 語氣與人稱

- 對使用者用「你」，不用「您」「使用者」「本人」。
- 用祈使句寫步驟：「按下開始」，不是「使用者可以按下開始按鈕」。
- 陳述事實，不推銷。**禁止**「業界領先」「完美支援」這類無法驗證的形容。

### 4.2 標題層級

- 全文**只有一個** H1（`#`），即專案名稱。
- 必要章節用 H2（`##`），其下最多再兩層（H3、H4）。**禁止** H5 以下。

### 4.3 程式碼區塊

- **必須**標註語言（```bash、```powershell、```json…）。
- 指令**必須**一行一條，**禁止**帶提示符（`$`、`>`、`PS>`），使用者才能整段複製。
- 需要說明的指令用行內註解，不要在區塊外另寫一段。

### 4.4 連結與圖片

- 庫內連結**必須**用相對路徑（`docs/使用說明.md`），**禁止**寫成絕對網址或本機路徑。
- 圖片**必須**放在庫內（建議 `docs/images/`），**必須**有替代文字。
- 外部連結**必須**寫清楚指向何處，**禁止**只寫「連結」「這裡」。

### 4.5 表格

規格、相容性、對照關係用表格，不用巢狀項目符號。

### 4.6 長度

必要章節齊全的前提下越短越好。超過 200 行時**建議**依 §2.1 外拆。

### 4.7 一句話定位與 About 簡介

README 第一節的一句話定位，與 About 的簡介**必須逐字相同**。

因此定位句**必須是純文字**——**禁止**使用 `` `程式碼` ``、`**粗體**`、連結或任何 Markdown 語法，否則貼進 About 會變成一串符號。

**結構**：

```text
<這是什麼>。<對使用者的價值>。
```

- 先講「這是什麼」，讓人判斷是不是自己要的；再講「對使用者的價值」，讓人知道值不值得下載。
- 長度**建議** 60 字以內，**上限** 100 字。
- **禁止**寫技術棧（「採用 TypeScript 與 Vite 建構」）——這是給使用者看的，不是給從業人員。技術棧寫在 `DEVELOPER.md`。
- **禁止**無法驗證的形容（「現代化」「流暢」「業界領先」），與 §4.1 一致。
- 尚未可用的專案**必須**在句中講明，例如「本專案剛起步，還沒有可用的版本」。

範例（虛構專案 `MYAPP`）：

```text
MYAPP 的存檔編輯器。選好資料夾按一下，就能改角色數值並直接寫回遊戲。
```

### 4.8 主題標籤

topics 決定別人搜不搜得到這個專案。**必須**涵蓋三個面向，每個面向至少一個：

| 面向 | 回答的問題 | 例子 |
| :--- | :--- | :--- |
| 領域 / 對象 | 別人找這類東西會打什麼？ | `monopoly`、`dos-game` |
| 專案型態 | 這是什麼樣的東西？ | `map-editor`、`game-patch`、`cli` |
| 主要技術 | 用什麼做的？ | `tauri`、`rust`、`typescript` |

- **建議** 3–6 個（平台上限 20 個）。
- **必須**全部小寫，詞間用連字號。
- **同一系列的專案必須共用至少一個 topic**，否則從其中一個找不到其他的。

### 4.9 網站

- 只填**離開這個儲存庫也能用**的東西：線上版、文件站、專案首頁。
- **禁止**填儲存庫自己的網址或 Releases 頁面——平台上已經顯示了，重複一次只是讓使用者點了一圈回到原地。
- 沒有這種東西就**留空**。留空是合規的，填錯不是。

## 5. 範例與註解慣例

### 5.1 佔位符

需要使用者替換的部分**必須**用角括號包住，內容為繁中描述：

```text
<專案名稱>-<版本號>-Setup.exe
```

**禁止**用 `xxx`、`your-app`、`TODO` 之類的佔位方式。

### 5.2 範例的可執行性

- 指令範例**必須**能原樣執行（佔位符除外），**禁止**貼未驗證過的指令。
- 範例中的版本號一律用 `v1.0.0`，路徑一律用相對路徑。
- 需要示範虛構專案時，一律用 `MYAPP`。**禁止**用真實的其他專案名稱。

### 5.3 註解

- 程式碼區塊內用該語言的註解符號，Markdown 內用 `<!-- -->`。
- 註解一律繁中，用來說明**為什麼**，不重複指令本身在做什麼。

### 5.4 驗證 About 與 README 一致

§4.7 要求逐字相同。**沒有驗證手段的規則會漂**——尤其中文的全形半形、空格差異用眼睛看不出來。發佈前跑這一段：

```powershell
$repo   = '<擁有者>/<儲存庫>'
$readme = 'README.md'

$about = (gh repo view $repo --json description | ConvertFrom-Json).description
$line  = ((Get-Content $readme -Encoding UTF8 |
           Select-String -Pattern '^> ' | Select-Object -First 1).Line -replace '^> ', '').Trim()

"About  : $about"
"README : $line"
"相同   : $($about -eq $line)"
```

前提是定位句以 `> ` 引述行的形式緊接在 H1 之後——這也是 [範本](templates/README.template.md) 的寫法。

## 6. 禁止事項

| 禁止寫進 README | 應該寫在哪 |
| :--- | :--- |
| 開發環境建置、相依套件安裝 | `DEVELOPER.md` |
| 建置、打包、測試指令 | `DEVELOPER.md` |
| 目錄結構、架構說明、設計決策 | `DEVELOPER.md` |
| 分支策略、commit 格式 | `DEVELOPER.md` |
| 逐版變更紀錄 | `CHANGELOG.md` |
| 發佈流程、產物命名 | `RELEASE_RULES.md` |

另**禁止**：

- 本機絕對路徑（`D:\...`、`/home/...`）、個人帳號、金鑰、憑證密碼。
- `TODO`、`待補`、`施工中` —— 沒寫好就不要留標題。
- 尚未發佈的功能。README 描述的**必須**是使用者現在下載得到的版本。
- 與 `CHANGELOG.md` 重複的完整更新清單。

About 另**禁止**：

- 簡介與 README 的一句話定位不同（含全形半形、空格的差異）。
- 定位句含 Markdown 語法——它要能直接貼進 About。
- 簡介寫技術棧或無法驗證的形容。
- topics 為空，或同系列的專案彼此沒有共用的 topic。
- 網站填儲存庫自己的網址或 Releases 頁面。

## 7. 檢查清單

發佈前逐項確認：

- [ ] 檔案在根目錄，UTF-8 無 BOM、LF、檔尾一個換行
- [ ] 七個必要章節齊全且順序正確
- [ ] 只有一個 H1
- [ ] 第一段就講清楚「這是什麼、給誰用」
- [ ] 「取得與安裝」寫明下載位置與系統需求
- [ ] 「快速開始」的步驟自己實際跑過一遍
- [ ] 所有指令區塊標了語言、沒有提示符、可原樣複製
- [ ] 所有連結可點、圖片顯示正常、圖片有替代文字
- [ ] 沒有任何建置 / 測試 / 架構內容（§6）
- [ ] 沒有絕對路徑、金鑰、個人資訊
- [ ] 沒有 TODO 與未發佈功能
- [ ] 描述的功能與目前最新發佈版本一致
- [ ] 末尾有指向 `DEVELOPER.md` 的入口

About（不進版控，改了不會有人 review，所以每次發佈都要看一眼）：

- [ ] 簡介與 README 的一句話定位**逐字相同**（用 §5.4 的指令驗，不要用眼睛）
- [ ] 定位句是純文字，沒有 Markdown 語法
- [ ] 簡介 100 字以內，沒有技術棧、沒有無法驗證的形容
- [ ] topics 涵蓋領域、專案型態、主要技術三個面向
- [ ] 同系列的專案共用至少一個 topic
- [ ] 網站欄位：有線上版才填，否則留空；沒有填成儲存庫自己的網址
